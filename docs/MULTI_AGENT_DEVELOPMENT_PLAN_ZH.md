# Minecraft Mod Studio 多智能体并行研发体系

> 版本：V1.0  
> 日期：2026-11-24  
> 适用仓库：tortletortle/minecraft-mod-studio  
> 目标：在不破坏 Java/Fabric 主线稳定性的前提下，让多个专业 Agent 并行完成研发、测试、集成和交付。

## 0. 核心结论

采用 **1 个总指挥 + 3 个治理角色 + 6 个并行研发席位 + 2 个独立验收席位**。

- 总指挥负责目标、优先级、资源分配和最终决策。
- 治理角色负责项目计划、架构契约、集成发布。
- 研发 Agent 在隔离分支和独立工作树中执行明确任务。
- QA 与安全 Agent 独立审查，不为自己写的代码签字。
- GitHub 是唯一项目事实来源；聊天记录不是任务状态数据库。

**并行不等于所有功能同时合并。** 允许同时研发，必须按依赖关系顺序集成。

### Main-first 集成硬规则（2026-11-25 起执行）

- 所有正式功能 PR 的 Base 必须是 `main`，不再建立长期堆叠 PR。
- 原始研发分支保留不改写；通过新的 `integration/*` 分支审计真实 merge-base 和独有提交，再整理到最新 main。
- 父功能先进入 main，子功能再基于更新后的 main 重整；不能仅修改 PR Base 来伪装完成 rebase。
- 每次合并后重新 fetch main，下一项集成必须记录新的 main SHA。
- CI 未启动、没有 runner/steps/logs 时标记为基础设施未执行，不得标为代码失败或测试通过。
- 操作细则和 PR #1 合并案例见 [Main 主线集成与分支收敛规则](MAINLINE_INTEGRATION_POLICY_ZH.md)。


## 1. 目标与边界

### 目标

1. 完成 Minecraft Java Edition / Fabric 主线产品，而不是只增加孤立原型。
2. 梳理现有开放 PR、分支中的重复工作、依赖关系和未验收项。
3. 让独立 Agent 在明确边界内持续实现、测试和修复。
4. 每个功能从需求、实现、测试、实机验收到发布都有证据。
5. 将可复用能力沉淀为插件、AI 工作流模板和模组资源模板。
6. Rust/Horizon 维持独立预研，不阻塞 Java 主线。

### 明确不做

- 不允许多个 Agent 同时修改同一个核心文件。
- 不允许 Agent 擅自改变公共 API、项目 JSON Schema 或 Fabric companion 协议而不更新契约和兼容测试。
- 不允许把 Draft PR、静态检查、本地单测或源码 ZIP 当成真实游戏验收。
- 不允许通过放宽安全限制、跳过失败测试或伪造日志制造“完成”。
- 不允许未经审查将实验分支合入 main。
- 不允许把 Horizon/Rust 预研变成 Java 主线依赖。

## 2. 组织结构

### A. 总指挥 Agent（CTO / Orchestrator）

唯一职责：调度整个研发系统。

- 维护产品目标、里程碑和优先级。
- 拆分任务，分配 Agent 和资源。
- 检查依赖图，决定哪些任务能并行。
- 处理跨 Agent 冲突和阻塞。
- 要求证据，不接受仅有口头完成声明。
- 汇总风险，决定返工、暂停或升级决策。
- 提交合并建议，由用户保留最终主线发布决策。

总指挥原则上不同时承担大规模功能编码，避免既当开发者又给自己验收。

### B. 三个治理角色

| 角色 | 职责 | 不允许做的事 |
|---|---|---|
| 项目经理 Agent | 任务拆分、优先级、依赖、看板、周报、阻塞跟踪 | 不擅自改变技术架构 |
| 架构与契约 Agent | 维护模块边界、数据模型、API、MCP 工具契约、版本兼容规则 | 不在未评审时重写各模块实现 |
| 集成与发布 Agent | 分支管理、合并顺序、冲突解决、构建流水线、版本和回滚 | 不以“能合并”代替验收，不绕过 QA |

### C. 六个并行研发席位

| 席位 | 责任域 | 主要工作 | 当前关联 PR / 分支 |
|---|---|---|---|
| R1 编辑器与 UI | 主编辑器、Workbench、双语、属性编辑、交互体验 | V19 维护入口、减少卡片、上下文编辑、Preset + Custom、视觉和键盘验收 | #25、main 的 V19 |
| R2 Fabric 运行时与游戏调试 | Fabric companion、Live Game Debugger、诊断、状态读取、截图和客户端生命周期 | companion 构建、类型化桥接、真实客户端验收、关闭清理 | #14–#16、#2–#13 |
| R3 AI God Mode | 命令发现、指令检索、任务规划、受限世界操作 | 命令清单、检索、风险预览、类型化事务、读回和回滚 | #18–#19、#22–#23 |
| R4 AI Project Operator | 项目级 MCP 操作、资源检索、兼容性分析、迁移规划 | 只读项目 API、Project IR、后续受控 ProjectPatch | #26–#27 |
| R5 模板生态 | AI 工作流模板、模组资源模板、模板路由和编辑器入口 | 两套注册表保持独立，定义组合接口与能力降级 | #21、#24 |

### D. 两个独立验收席位

| 席位 | 职责 | 独立性要求 |
|---|---|---|
| Q1 QA / 游戏验收 Agent | 测试计划、自动化测试、浏览器、Gradle/Fabric 构建、Minecraft 实机、回归 | 不验收自己实现的功能；必须记录环境和复现步骤 |
| Q2 安全 / 兼容性 Agent | MCP 权限、命令边界、包签名、资源输入、跨版本和第三方模组风险 | 有权阻止高风险变更合并；不得用“功能正常”替代安全审查 |

### E. 按需专项研发

以下工作暂不占用六个核心席位的固定资源，按里程碑启动：

- Structure Studio：独立建筑/地牢工作流，先完成 Minecraft 26.2 实机验收，再讨论主编辑器集成。
- UMPD / Schema Engine：协议扫描和数据模型研究，先验证真实模组语料，再决定产品集成。
- Horizon / Rust：仅 H0 预研；Java 主线成熟后才可申请 H1 原型。
- 视觉设计审查：由 R1 与独立设计评审共同负责，不把 UI 截图或生成效果图当作真实交互测试。

## 4. 任务依赖与集成顺序

### 阶段 0：先把研发现场整理成可控状态

- 重新核对 main HEAD、维护源码、所有开放 PR、分支基线、堆叠关系和 CI。
- 明确 V19 是当前维护入口，V23/V25 是历史快照；未经验证不得切换维护入口。
- 将 PR 标记为：可合并候选、依赖未完成、待验收、重复/过时、研究保留。
- 为每个现有 PR 指定唯一责任 Agent。
- 建立路径所有权和公共接口登记。
- 不在此阶段批量合并。

**阶段 0 退出条件：** 每个开放 PR 有责任人、依赖、验收标准、当前证据和下一步；不存在无人负责的主线阻塞。

### 阶段 1：建立可复现的 Java/Fabric 工程基线

- R1 + R2 + 集成 Agent：固定 V19 维护入口和可复现构建。
- QA：复核 PR #1 的工程验收工作流。
- R2 + QA：逐项处理 PR #12 已记录的资源归档路径、动画姿态差异、预算错误提示和测试世界清理问题。
- 所有功能测试都要绑定明确 Minecraft、Java、Fabric Loader、Fabric API 和操作系统版本。

**退出条件：** 主线源码映射明确；基线构建和回归可复跑；已知失败项有修复或明确阻塞记录。

### 阶段 2：游戏运行时与 AI 操作能力

可以并行：
- R2：按 #14 → #15 → #16 的依赖完成 Live Game Debugger。
- R3：按 #18/#19 → #22 → #23 的依赖完成 AI God Mode。
- R4：推进 #26/#27 的只读 Project Operator，先不引入写操作。

**退出条件：** 真实 Fabric companion 可连接；工具能力来自实际握手；只读和写操作严格区分；写操作具有预览、确认、读回、失败补偿和可验证回滚。

### 阶段 3：编辑器体验与可复用能力

可以并行：
- R1：推进 #25 UI Workbench，完成双语、属性编辑、Preset + Custom 和浏览器验收。
- R5：推进 #21 AI 模板库与 #24 模组模板库，保持两个 Schema 和职责独立。
- R6：推进 Extension Engine V0.9 的真实浏览器、多标签、持久化和恢复验收。

**退出条件：** 模板可被正确检索和预览；能力缺失会安全降级；插件包安装、权限、卸载、回滚和数据恢复有浏览器证据；UI 有真实截图和交互记录。

### 阶段 4：专项功能接入

- Structure Studio：先做 26.2 数据包实机测试，再决定作为独立工具、插件还是主编辑器模块。
- UMPD：先完成真实模组样本审计、误报/漏报分析，再决定是否进入 AI 适配链。
- Schema Engine：先建立稳定 Schema 契约，再由 R4/R5 消费。
- Horizon/Rust：继续独立预研，不共享 Java 主线发布门禁。

### 阶段 5：系统级验收与发布

- 全量回归：编辑器、MCP、Fabric companion、模板、插件、资源导入/导出。
- 安全审查：未信任模组元数据、命令注入、权限边界、包完整性和降级路径。
- 真实 Minecraft 测试：新建一次性世界，保留日志、截图、配置、JAR 哈希和复现步骤。
- 生成发布说明、已知问题、升级/回滚说明。
- 由总指挥提交合并建议，用户决定主线合并与正式发布。

## 5. Git 分支与文件所有权

### 分支规则

- main：唯一稳定集成基线，任何研发 Agent 都不能直接提交。
- agent/<domain>/<task-id>：每个独立任务一条短生命周期分支。
- research/<topic>：研究方向，禁止自动合入 main。
- 已有 PR：优先复用、拆分或关闭过时分支，避免为同一能力再造一条重复分支。
- 每个 Agent 使用独立 worktree / checkout；不能在同一工作目录同时改文件。
- 每个 PR 必须记录 base SHA、head SHA、依赖 PR、测试命令和验收证据。

### 文件所有权建议

| 路径 / 资源 | 主责任席位 | 协作规则 |
|---|---|---|
| Minecraft_Mod_Studio_V19.html | R1 | 核心文件单写者；其他 Agent 通过接口提案和独立模块交付，不直接并发修改 |
| Fabric companion / Java 源码 | R2 | R3/R4 通过稳定桥接契约消费，不自行复制 companion 实现 |
| Python MCP 服务 / tools | R3、R4 按模块分区 | 共享注册入口由架构 Agent 审核；工具 schema 变更必须附契约测试 |
| docs/ai-templates/ | R5 | AI 工作流模板专属 |
| docs/mod-templates/ | R5 | 模组资源模板专属；不得与 AI 模板合并成一个无类型目录 |
| research/extension-engine/ | R6 | 插件运行时独占；与编辑器通过版本化 Host API 连接 |
| structure-studio/ | 专项 Structure Agent | 独立模块，实机验收前不改主编辑器 |
| .github/workflows/ | 集成 Agent | 各 Agent 提交 workflow 修改前先声明，避免覆盖其他流水线 |
| docs/PROJECT_STATUS_DASHBOARD_ZH.md | 项目经理 Agent | 只写已验证状态、证据、提交和阻塞，不写推测性完成率 |

**关键规则：** Minecraft_Mod_Studio_V19.html 是单文件核心，必须采用单写者机制。若多个功能都需要改它，应先通过模块化提案、独立脚本/模块和接口契约降低冲突，再由 R1 集中集成。

## 6. 标准任务卡

所有任务必须采用以下字段，缺字段的任务不能进入 Ready：

| 字段 | 要求 |
|---|---|
| Task ID | 唯一编号 |
| 目标 | 一句话描述可观察结果 |
| Owner | 唯一主责 Agent |
| Reviewers | 至少一名不同于作者的审查 Agent |
| Branch / Base SHA | 隔离分支和准确基线 |
| Allowed paths | 允许修改的文件范围 |
| Forbidden changes | 明确禁止触碰的功能和接口 |
| Dependencies | 前置任务 / PR |
| Acceptance criteria | 可验证、可判定的通过条件 |
| Tests | 精确命令、环境和预期结果 |
| Evidence | 日志、工作流、截图、JAR 哈希、报告链接 |
| Rollback | 失败后如何撤销或恢复 |
| Status | Backlog / Ready / Active / Blocked / Review / Verify / Merge-ready / Merged / Released |

### 状态机

~~~text
Backlog
   |
 Ready
   |
 Active <---- Blocked
   |
 Review
   |
 Verify
   +---- fail ----> Active
   |
 Merge-ready
   |
 Merged
   |
 Released
~~~

“代码写完”只能从 Active 进入 Review，不能直接跳到 Merged 或 Released。

## 7. Agent 协作协议

每个 Agent 的启动简报必须包含：

1. 项目当前基线和任务目标。
2. 允许修改的路径及禁止修改的路径。
3. 上游/下游接口和依赖。
4. 当前已存在的实现，禁止重复造轮子。
5. 验收标准与测试命令。
6. 交付格式和证据要求。

执行期间只发送有价值的事件：

- STARTED：确认基线、分支和任务范围。
- PROGRESS：报告已完成的可验证子目标。
- BLOCKED：描述阻塞、证据、需要谁决策。
- HANDOFF：提交 SHA、变更摘要、测试结果和剩余风险。
- REVIEW_REQUEST：请求另一 Agent 独立审查。
- ACCEPTED / REJECTED：由验收席位给出结论和依据。

不要求 Agent 不断输出思考过程；要求它持续产出代码、测试、报告和可复现证据。

## 8. 独立验收等级

| 等级 | 名称 | 证据 | 可以声称什么 |
|---|---|---|---|
| L0 | 设计完成 | 设计文档、接口契约 | 方案已定义 |
| L1 | 静态验证 | 语法、Schema、静态规则 | 静态检查通过 |
| L2 | 单元/集成测试 | 自动化测试日志 | 指定测试通过 |
| L3 | 浏览器验收 | Chromium 等真实浏览器交互记录 | 指定浏览器流程通过 |
| L4 | 构建验收 | 指定 JDK/Gradle/Fabric 构建产物和哈希 | 指定版本构建通过 |
| L5 | 游戏实机验收 | 真实客户端/服务端、世界、日志、截图和复现步骤 | 指定游戏场景通过 |
| L6 | 发布验收 | 全量回归、安全审查、升级/回滚和发布记录 | 指定版本可发布 |

每个功能标注最高已达到等级和未达到的下一等级。不同功能不能互相借用测试证据。

## 9. 合并门禁

一个 PR 必须同时满足：

- 目标分支和依赖关系正确。
- 只修改声明范围内的文件。
- 有独立 Reviewer，且审查者不是作者。
- 自动化测试确实执行；Runner 未分配、工作流没有 steps 时标记为“未执行”，不是通过。
- 没有静默删除功能、跳过测试或降低安全限制。
- 公共 API / Schema / companion 协议有版本和兼容性说明。
- 有失败用例和已知限制。
- 需要实机验收的功能有真实游戏证据。
- 集成 Agent 复核冲突、回滚路径和主线回归。

任何 Agent 都不能自行批准自己的 PR 或将其直接合入 main。

## 10. 调度策略与并行度

### 推荐并行度

- 1 个总指挥。
- 3 个治理角色。
- 最多 6 个活跃研发 Agent。
- 2 个独立 QA / 安全席位。

不建议第一天就启动十几个编码 Agent。当前分支和 PR 数量已经很高，先降低冲突比增加并发更重要。

### 动态调度规则

- CPU/构建资源紧张时，减少同时运行的 Gradle/浏览器实机任务，不减少代码审查。
- 核心接口未冻结时，允许研究和独立模块开发，不允许下游批量接入。
- 同一路径已有活跃写者时，新任务必须排队或改成接口提案。
- Blocked 超过一个工作周期时，由总指挥重新拆分、替换路径或明确升级决策。
- QA 发现回归时，暂停依赖该基线的下游合并，不停止无关泳道。
- 每个 Agent 完成一个可独立验收的切片就交付，不等整个大任务完成才提交。

## 11. 看板与度量

GitHub Projects 作为任务状态入口，Pull Requests 作为代码交付入口，Actions 作为自动化证据入口，文档作为架构与决策记录入口。

建议字段：

- Workstream
- Owner Agent
- Priority
- Status
- Dependency
- Branch
- PR
- Acceptance Level
- CI Status
- Game Test Status
- Last Evidence
- Blocker
- Target Milestone

每周度量：

- 已验收任务数（不统计单纯关闭的任务）。
- 从 Ready 到 Merge-ready 的周期。
- 首次验收通过率。
- 回归缺陷数和严重度。
- PR 冲突率。
- Blocked 任务数量与持续时间。
- L4/L5 验收覆盖率。
- 未关闭的安全问题。

不以 Agent 输出字数、提交次数或 PR 数量作为生产力指标。

## 12. 第一轮实际执行清单
